# Bridge 目标架构提案

状态：已完成候选设计与独立源码可行性审查；设计快照和实施任务已发布到 [全局架构总览 Issue](https://github.com/Lycidas97/claude-desktop-bridge/issues/199)，尚未启动产品实现。关系图见 [architecture-proposal.mmd](architecture-proposal.mmd)。

源码基线：`e58eddb2e3d50f3b13749da8a2bede74a8c24e50`。当前实现见 [ARCHITECTURE.md](ARCHITECTURE.md)，安全边界见 [SECURITY.md](SECURITY.md)。本文讨论目标职责、依赖和迁移，不替代当前实现说明。

关系图表达模块协作、请求与事件通路，不表示 import 依赖或严格的执行时序。图中的请求处理是现有能力的职责集合，不要求新增统一转发层。

## 1. 先定职责，再移动文件

Bridge 保留客户端、Desktop 后台服务、Relay 三个现有运行边界。各边界内部采用职责明确的模块，不增加微服务或通用插件平台。

目标是让新增页面和新增业务有可预测的修改范围：页面组合已有能力，客户端状态转换有明确归属，Desktop 业务操作通过现有请求入口提供，原生接入继续封装在本地边界内。

已有稳定能力优先保留：配对与 E2EE、Relay/WebRTC 路径、原生会话调用、收据与重放、被动成果采集。文件长短不作为是否重构的依据。

## 2. 产品与运行边界

| 边界 | 拥有的职责 | 不拥有的职责 |
| --- | --- | --- |
| 客户端：手机与 Electron renderer | 页面、交互、草稿、缓存投影、用户操作提交 | 会话执行、原生排队、权限裁决 |
| Desktop 后台服务 | 本机原生接入、请求处理、配对设备、收据、事件同步、成果与业务存储 | 第二套模型执行器或会话调度 |
| Claude Desktop | 原生会话、执行、消息队列、授权与 transcript | Bridge 业务数据库与客户端界面 |
| Relay | 密文路由、离线密文暂存、设备投递、无正文唤醒 | 明文业务、会话索引、密钥、邮件处理 |
| 业务模块：邮件等 | 业务记录、读取与更新规则、明确的业务接口 | 通用 inspector 能力、独立执行队列 |

Electron 主窗口是后台服务的客户端。关闭窗口不关闭收件、配对、原生连接和同步；后台服务统一创建和释放它拥有的资源。

## 3. 客户端：页面、会话显示、状态接入分开

### 页面与共享显示

- 普通会话页负责目录和选择 sessionId；助理页负责绑定 sessionId、邮件/设置子视图。未来业务页面自己决定组合哪些已有能力。
- 共享 `ConversationView` 负责单会话消息流、composer 与直接交互；平台壳持有导航、返回键、多栏布局及管理弹层。
- 业务通过具体组件和必要插槽组合。保留有类型的时间线条目，不增加通用 `extensions`、`beforeSend` 或页面插件注册表。
- `ConversationView` 本体不主动读取邮件 Provider；`MailCard` 等业务叶子可继续通过自己的 Provider 按需读取业务数据。
- 草稿、图片附件、上传和发送状态由卸载边界外的稳定 owner 持有，以 `(hostId, sessionId)` 隔离；不因视图拆分引入磁盘草稿持久化。

这一部分由 [受控对话重构 Issue](https://github.com/Lycidas97/claude-desktop-bridge/issues/196) 跟踪，复用现有共享叶子与两端能力对齐任务。

### 手机与桌面分别提供数据

手机使用现有 `useMobileBridge`、加密请求、事件恢复和本地保险库；桌面使用现有本地 IPC 请求与加载状态。两者适配为显示需要的数据和动作，不强制共用同一 transport 或缓存生命周期。

显示契约包括投影后的消息条目、加载状态、权限/prompt、不确定投递及必要动作。提交动作保留 requestId。两端对 localTurns、分页窗口的现有差异留在适配端。

### 客户端状态规则归位

保留现有 React 状态源及按连接管理的闭包，先解决状态转换规则分散的问题：

1. 集中当前 host 数据的建立、替换与清空规则。连接状态、错误、配对确认按具体入口决定，不把所有场景合成一次全量 reset。
2. 集中事件和 RPC 结果对同一会话投影的更新规则，复用已有 reducer。请求收发负责 I/O，已定型结果交给明确的状态转换。
3. 历史、evidence、附件缓存分别维护自己的载入与更新操作；调用方不必获得改写整份状态的通用权限。
4. `useMobileBridge` 保留生命周期组合和面向调用方的动作。真正只做请求转发的包装，可在规则稳定后再按实际复用提取。
5. 邮件分页与缓存由业务层持有，通过明确的当前 host 接口使用 vault；不能把当前配对 crypto 随意改成 crypto map 查询，临时身份与确认后身份的提交时机不同。

上述职责先在原模块内收拢，再决定是否分文件。当前不引入外部 store 或大型 `BridgeClient`。

## 4. Desktop：组装、请求操作、原生接入、投影与存储分开

### 后台服务组装

现有 `service-runtime` 是资源生命周期的组装入口：创建配置、存储、业务服务、原生接入、请求入口与传输；关闭时释放这些实例。窗口、Provider、MCP 适配器不另建后台服务。

`app/` 中的应用组装与可复用平台工具需要在职责上区分。仅当真实依赖需要时迁移路径、诊断等工具，不建立装所有杂项的 `shared/` 目录。

### 请求操作

保留现有统一请求 facade。逐步把自然聚合的操作从路由/大 Controller 内归到明确的模块：

| 操作集合 | 职责 | 复用的现有能力 |
| --- | --- | --- |
| 会话操作 | 创建、发送、配置、权限答复、队列动作 | 原生 broker、收据与事件 |
| 主机与设备操作 | 配对、撤销、主机配置、状态查询 | 配置与 host transport |
| 成果与文件操作 | evidence、预览、上传/下载 | evidence/transfer 模块 |
| 助理业务操作 | 绑定、邮件分页、业务处理状态 | assistant-mail 服务与业务存储 |

这些是职责边界，不要求每个集合新建 service 类或经过额外的 application ops 转发层。现有 broker 的 `startTurn(NativeInput)` 已经封装幂等收据、调用前持久化、原生排队和不确定态处理；调用方可以直接复用。只有多个真实调用方需要相同的额外编排规则时，才提取共同操作。

远程请求入口负责设备鉴权、解密和协议校验；本地入口保留自己的 IPC/token/来源约束。可复用的操作继续经过现有请求 facade，但不强制所有入口都转换成 `BridgeRequest`：配对、设置、诊断等本地管理能力仍走既有本地方法。手机请求、本地完整管理、邮件 MCP 的能力范围分别约束；邮件 MCP 继续使用独立 token 与窄工具入口。

### 原生接入与状态投影

原生模块拥有 inspector 连接、明确的 LocalSessions 操作、原生事件归一化与 transcript 接入。原生调用继续使用收据和事件能力，不暴露任意 evaluate。

broker 当前已通过组装入口注入 `ConversationStateStore`、`SessionEventLog` 和收窄的 evidence 接口，没有依赖整个 Controller。保留这一边界；仅按实际使用收窄具体存储/事件协作类型，必要时整理目录归属。目录之间的类型引用本身不是新增抽象层的理由，不预建 NativePort/Repository 体系。

Controller 的长期职责收敛到组合现有状态、生成主机快照、发布已发生的变化与能力，而不是成为每种业务数据库和执行细节的实现位置。

### 存储各有权威范围

| 数据 | 权威归属 | 其他部分如何使用 |
| --- | --- | --- |
| 会话、原生队列、权限与 transcript | Claude Desktop | broker 转发与读取，客户端显示投影 |
| 请求幂等键、投递收据 | ConversationStateStore | 提交与原生事件推进；不确定不自动重发 |
| Bridge 同步事件与 seq | SessionEventLog | 事件恢复，不作为原生历史补页来源 |
| 成果清单、预览快照 | EvidenceStore | 被动采集、按需预览/传输 |
| 邮件、绑定、分析等业务事实 | assistant-mail 私有存储 | 有界索引、分页读取、业务变更通知 |
| 客户端缓存 | vault 与各自客户端 owner | 加快显示与恢复，不升级为服务端事实 |
| 草稿与附件交互状态 | 客户端稳定父级 | 供普通页与助理页的对话视图使用 |

业务模块拥有自身记录的规则与持久化；对原生会话只保存引用和投影，不取得执行、队列或权限所有权。

不为了统一接口合并现有数据库，不迁移旧会话数据，不重建配对身份。

## 5. 业务扩展：一条明确接入路径

以个人助理后续待办为例：

1. 客户端助理功能增加具体面板，组合现有对话，不复制消息流。
2. 需要新的远程业务操作时，增加协议类型、边界校验及 capability；本地和远程入口分别保留权限边界。
3. Desktop 请求处理调用业务服务；业务服务持有对应存储规则。MCP adapter 仅映射被允许的业务操作，不获得完整后台控制或 inspector 权限。
4. 业务记录提交后提供有界变化索引与分页；同步更新快照发布判定、客户端投影与重连恢复，不能只加一个 snapshot 字段。
5. 需要会话执行的行为仍通过现有 broker；邮件自动投递门禁保持现有要求，不因架构重构启用。

邮件规则归位采用显式协作：提供会话/项目视图、原生可用性，以及已确认成功的归档/删除通知。目录暂时缺席继续表示 `missing`，不能当成删除；单靠目录 changed 回调不能替代成功操作通知。迁移时同时处理 RPC、broker 回调和 fixture 的全部调用方，保持绑定暂停与恢复语义。

业务记录变更继续显式接入事件、快照发布判定及重连分页。quota 的请求查询与 mail 的持久接收是不同生命周期，不强制实现统一的 `handle/snapshot/changed` 插件形状。待办是否独立模块、使用哪个数据库，留给实际业务任务决定。

无需为每个新面板修改连接重连算法。新增跨端业务仍需显式修改契约、宿主入口和客户端接入；架构不会消除这些真实边界。

## 6. 协议与 Relay

保留 `@bridge/protocol` 现有包边界：协议类型、校验、capabilities、配对、加密、分帧、传输及共享 IPC 契约。新增业务不把宿主数据库、React 状态或 inspector 实现带进此包。

必要时在包内按契约、加密、传输组织文件，稳定既有导出和构建顺序；没有独立消费者或构建需求前，不拆成多个新 package。

Relay 保留独立密文职责，不承接助理、待办或会话投影。WebRTC、LAN、WSS 使用现有密文信封与回退语义；传输 ACK、RPC 返回、原生接收与业务处理完成是不同事实。

## 7. 依赖约束

| 调用方 | 允许依赖 | 应避免的依赖 |
| --- | --- | --- |
| 客户端页面 | 共享显示、自己的业务模型、明确数据/动作适配 | 原生 inspector、Relay 实现、完整客户端内部 refs |
| 共享对话视图 | 已定型数据、明确动作、共享叶子与必要插槽 | 页面导航策略、业务数据加载、传输实现 |
| Desktop 组装入口 | 需组装的具体模块 | 业务操作实现细节 |
| Desktop 请求操作 | 原生 broker、成果、设备、业务服务的明确接口 | UI 状态、socket 路由细节 |
| 原生接入 | inspector/transcript、实际所需的收据与事件协作能力 | 整个 Controller、业务页面 |
| 业务服务 | 自己的存储、必要的明确协作接口 | 任意 inspector、第二套执行队列 |
| Relay | 路由契约、密文存储与唤醒 | 业务正文、解密密钥、会话模型 |

组装根允许了解具体实现；调用方只拿到完成职责所需的接口。不要为了让箭头漂亮增加转发层。

## 8. 分阶段迁移

| 阶段 | 具体工作 | 完成标准 |
| --- | --- | --- |
| 1. 已有前端重构 | 完成共享叶子与两端能力对齐；保留顶层消息节点和稳定 key | 既有两端功能与滚动场景通过 |
| 2. 客户端状态归属 | 收拢当前 host 数据转换，再收拢同一会话的事件/RPC 更新；删除退役无用 props 链 | 新增投影字段不必到多个入口复制初始化/清空规则 |
| 3. 页面与对话解耦 | 实施 Issue 196 的四个现有调用位置、稳定草稿/附件 owner、两端小适配器 | 助理页不再嵌入整个工作区 |
| 4. Desktop 操作归位 | 按新增业务或触及的自然职责提取请求处理，保留请求 facade 与调用契约 | 新业务不扩散到原生连接与 Relay |
| 5. 依赖清理 | 按实际使用收窄存储/事件协作类型；必要时整理平台工具归属 | 保持现有窄依赖，只清理确认存在的耦合 |

上述是减少冲突和返工的建议顺序。阶段 2、3 需要先对齐数据/动作契约、稳定草稿及上传 owner、host/session 切换语义；同文件修改顺序落地，阶段 3 不以全部状态整理完成为前置。阶段 4、5 按具体调用证据安排，不为完成全仓目录改名先搬完全部代码。

退役 store API 是独立可选减法，不阻塞对话重构。不能按方法名称或行号区间删除：provider 初始化仍有内部 seed 调用，旧 queue 方法仍依赖 lane 方法，需检查完整调用链；保持 SQLite 表和旧记录，并保留不导入旧数据、原生收据恢复等仍有效的测试。

不改变协议版本、设备身份、存储格式、传输语义或原生执行权威；确需改变时另列兼容性任务。

## 9. 验证

设计文档本身不运行产品套件，也不宣称实现已验收。实施 PR 按 AGENTS 路由和现有流程执行：评审前 typecheck 与相关测试，客户端 UI 加 browser；评审收敛后在被审 SHA 上执行一次 ci:local。

迁移验收关注现有行为：主机切换和忘记、配对失败不覆盖旧身份、解密后在线证明、重连事件恢复、投递回执与不确定态、禁止旧执行请求自动重发、两端历史分页锚点、草稿/附件隔离、邮件关联投影、后台服务关窗存活及明确关闭。

现有 hook ref/effect 顺序 mock、Controller prototype harness、MediaPreviewProvider QA 路径耦合需要在对应 PR 调整。它们是迁移约束，不是预先重写全部测试的理由。

## 10. 设计取舍

- 不选择一次性重写：已有安全边界和运行时能力可以直接保留。
- 不选择只拆大文件：转换规则仍散落时，文件变小不会减少维护地点。
- 不选择统一万能状态库或插件平台：当前问题是明确职责与生命周期，不是缺少框架。
- 不选择按每个子系统提新 package：先在既有 workspace 内形成真实模块边界，避免无消费者的包和构建成本。
